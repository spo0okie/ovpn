# Тесты

Два уровня:

1. **Поведенческие тесты** (есть сейчас) — быстрые, без внешних зависимостей,
   гоняются локально и в CI на каждый push.
2. **Интеграционные прогоны в Docker** (планируются) — полный цикл с настоящими
   openssl/openvpn/инвентори; критерий приемки — реально работающий туннель.

## Уровень 1: поведенческие тесты

```sh
bash tests/run.sh
```

Зависимости: `bash`, `jq`, coreutils. Внешние команды подменяются
заглушками через PATH, openssl не вызывается (ключ/серт подкладываются
фикстурами — скрипты пропускают генерацию по своим же проверкам
`[ -s $keyfile ]`). Каждый сценарий выполняется в чистой песочнице
`mktemp -d`, боевые данные не затрагиваются.

| Файл | Что делает |
|---|---|
| `run.sh` | запуск всего: `bash -n` всех скриптов + все `test_*.sh` |
| `helpers.sh` | песочница, assert'ы, маршруты заглушки curl |
| `stubs/curl` | пишет вызовы в лог, отвечает по таблице «подстрока URL → JSON» |
| `stubs/google-authenticator` | кладет фиксированный секрет в `--secret=` |
| `test_lib.sh` | функции `_lib`: маски, работа с инвентори |
| `test_usr_new.sh` | CCD-логика `usr.new`: выдача IP, миграция подсетей, noupdate, 2FA |
| `test_multisite.sh` | multisite: конвертация 2FA-адресов, `_ccd.check`, `usr.gen.ccd` |

Правила:
- каждый `test_*.sh` самодостаточен (свой sandbox на сценарий) и
  подхватывается `run.sh` автоматически по маске;
- тесты фиксируют **текущее** поведение скриптов — при рефакторинге
  (см. `multisite/UNIFICATION.md`) сначала пишется/проверяется тест,
  потом меняется код; падение теста после рефакторинга = изменение
  поведения, которое нужно либо починить, либо осознанно принять
  правкой теста в том же коммите.

## Уровень 2: интеграционные прогоны в Docker (план)

Место: `tests/integration/` (docker-compose.yml, Dockerfile'ы, сценарии).
Запуск планируется как `bash tests/integration/run.sh` — поднять окружение,
прогнать сценарии, погасить. Требуется Docker (Docker Desktop / WSL2 —
`/dev/net/tun` и `NET_ADMIN` для контейнеров доступны).

### Контейнеры

| Сервис | Содержимое | Зачем |
|---|---|---|
| `server` | debian/alpine + openvpn, openssl, jq, google-authenticator; репозиторий смонтирован в `/etc/openvpn` | здесь выполняются provision-скрипты и поднимается настоящий openvpn-сервер из сгенерированного `server.conf` (`cap_add: NET_ADMIN`, `/dev/net/tun`) |
| `client` | openvpn | подключается сгенерированным клиентским конфигом к `server`; критерий — `Initialization Sequence Completed` + ping через туннель |
| `inventory` (опциональный profile) | `spo0okie/inventory:v1` + `mysql:8.0` | проверка реальной выдачи/закрепления IP вместо заглушки curl |

Без profile `inventory` сценарии работают с пустым `inventoryApiUrl`
(пустые CCD) либо с заглушкой как в уровне 1.

### Профиль inventory: детали

Приложение инвентори ([arms](https://github.com/spo0okie/inventory)) —
Yii2 + MySQL, образ `spo0okie/inventory:v1`; при старте контейнер сам
дожидается БД (хост `arms-db`), прогоняет миграции и поднимает apache.
За основу берется `docker/docker-compose.yml` из репозитория arms.

Что важно для тестового окружения:

- **API**: базовый URL `http://<app>:8088/web/api`. Используемые
  скриптами endpoint'ы: `net-ips/search?name=`,
  `net-ips/first-unused?text_addr=`, `net-ips/create`, `net-ips/update`,
  `users/search?login=`, `PUT users/<id>` (поле `ips`).
- **Авторизация**: при дефолтном `useRBAC=false` API открыт — логин и
  пароль в `inventoryApiUrl` тестового `_config` игнорируются, что для
  тестов и нужно.
- **Схема БД**: миграции в arms инкрементальные — на пустой БД схему не
  создают. Нужен стартовый дамп (`tests/_data/arms_demo.sql` из
  репозитория arms), путь к нему передается через переменную окружения
  и монтируется в `/docker-entrypoint-initdb.d` mysql-контейнера;
  миграции контейнер приложения докатит сам.
- **Фикстуры**: `first-unused` требует записи в `networks` с
  `text_addr`, точно равным `vpnnet` тестового конфига, а привязка IP —
  пользователя с известным `Login`. Сеть создается SQL-вставкой после
  старта (API-контроллера для networks нет), тестовый пользователь —
  вставкой в `users` или берется из демо-дампа.

### Приемочные сценарии

Нумерация — она же план реализации, сверху вниз:

1. **Инициализация сервера**: `_reset.sh` на чистом окружении → созданы
   CA, серверный ключ/серт, dh, ta.key, `server.conf`, пустой CRL;
   openvpn-сервер стартует с этим конфигом без ошибок.
2. **Генерация пользователя**: `usr.new user1` → сертификат подписан CA
   (`openssl verify`), ключ соответствует сертификату (сравнение
   modulus), `.ovpn` содержит все inline-секции; **клиент подключается
   к серверу этим конфигом** — туннель поднялся, ping прошел, выданный
   в CCD адрес совпал с фактическим.
3. **Отзыв пользователя**: `usr.revoke user1` → серийник в CRL, папка
   уехала в `revoked/` с таймстампом; повторное подключение этим же
   конфигом **отвергается** сервером (crl-verify).
4. **Массовая генерация**: `usr.new user{1..10}` → 10 валидных
   сертификатов без коллизий серийников; с инвентори — 10 уникальных
   IP; все 10 конфигов поочередно поднимают туннель.
5. **Массовое добавление сетей в CCD**: пользователи созданы со старым
   набором `subnets` → в `_config` меняются `subnets` +
   `previousSubnets` → обход `_renew` всех пользователей → все
   стандартные CCD обновлены (клиент получает новые маршруты — виден
   push в логе клиента), кастомный CCD не тронут (`ccd.new`/`ccd.old`
   рядом).
6. **2FA**: `use2fa=1` → `google.txt` создается настоящим
   google-authenticator, секрет валидный base32.
7. **CRL-обслуживание**: `upd.crl` → CRL перевыпущен, nextUpdate ~720
   дней.
8. **Инвентори** (profile inventory): закрепленный IP возвращается тому
   же пользователю; свободный выдается последовательно; IP
   регистрируется за конфигом и пользователем.
9. **Multisite**: `usr.new + usr.gen.ccd + usr.generate` → конфиги по
   сайтам; обычный конфиг поднимает туннель к серверу сайта; 2FA-конфиг
   содержит `auth-user-pass`; `usr.push` раскладывает CCD на «сервер
   сайта» (второй контейнер по ssh).

Сценарии 1–5 — минимум для начала унификации; 6–9 — по мере
переноса соответствующих фич.

### Соглашения для интеграционных тестов

- каждый прогон начинается с чистого состояния (fresh volume), никакого
  общего состояния между сценариями;
- секреты тестового окружения (пароли БД инвентори и т.п.) — только
  тестовые, захардкоженные в compose: это фикстуры, не боевые данные;
- прогоны не входят в обязательный CI (медленные, требуют
  привилегированных контейнеров) — запускаются локально перед
  merge/release; отдельный workflow можно добавить позже.
