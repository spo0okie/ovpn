# Мультисайтовый сценарий

> **Устаревший site-центричный вид.** Канон целевой модели — инстанс-модель
> (`plans/migration-instance-model.md`, `plans/1788590603632-provision-scenarios.md`).
> Скрипты этого каталога удалены: их поведение покрыто корневыми скриптами
> (`usr.new` с `instances`, `usr.gen.ccd <user> <instance>`, единый `usr.publish`).
> Разовая миграция данных multisite → инстансы — `migrate-to-instances.sh`.
> Этот документ оставлен как историческая справка по сценарию 2
> (N серверов × 2 инстанса, отдельный узел управления).

Вариант скриптов для организации с несколькими площадками (сайтами).

## Архитектура

В отличие от базового варианта (скрипты живут на самом OpenVPN-сервере),
здесь используется **центральный админ-хост**:

- админ-хост хранит CA, папки клиентов (`clients/`), генерирует ключи,
  сертификаты и клиентские конфиги **для всех сайтов сразу**;
- на каждом сайте стоит свой OpenVPN-сервер (обычно два инстанса:
  обычный на `$port` и 2FA на `$port2fa`);
- админ-хост пушит на серверы сайтов по ssh только CCD-файлы и секреты
  google-authenticator (`usr.push`), и может забирать их обратно (`usr.pull`);
- готовые конфиги доставляются пользователю через Nextcloud (шара на
  пользователя), пароль от ключа и секрет 2FA — через СМС-шлюз (`usr.send`);
- IP-адреса клиентов учитываются в инвентори (`_lib.inv`).

Режим подключения (обычный/2FA) определяется **per-user/per-site** по тому,
в какой подсети лежит адрес из CCD-файла (`_ccd.check`): у каждого сайта в
`_config` задается `<site>_openvpn_lan` и, опционально, `<site>_openvpn2fa_lan`.

## Соответствие файлов базовому варианту

| Файл | Отношение к базовому варианту |
|---|---|
| `usr.new` | **заменяет**: только создает папку клиента с обертками `_generate`/`_send`/`_push`/`_pull`/`_disable`/`_enable` |
| `usr.generate` | **новый**: реальная генерация — ключ с паролем, сертификат, конфиги по всем сайтам (+ вариант для OpenVPN Connect), секрет 2FA |
| `usr.gen.ccd` | **общий** — живет в корне: `usr.gen.ccd <user> <site>` генерирует/обновляет `ccd.<site>` (с миграцией через `previousPushRoutes`/`<site>_previous_openvpn_lan`) |
| `usr.disable` / `usr.enable` | **заменяют**: переименование `ccd.<site>` ↔ `ccd.<site>.disabled` + push на сайт (в базовом — линк/удаление линка в локальном ccd-каталоге) |
| `usr.push` / `usr.pull` / `usr.push.inv` | **новые**: синхронизация CCD/2FA-секретов с серверами сайтов и инвентори |
| `usr.send` | **общий** — живет в корне: доставка конфигов через Nextcloud или почту + СМС (включается `nextcloudUrl`/`mailSmtpUrl`/`smsApiUrl` в `_config`) |
| `_ccd.check` | **новый**: определение режима (OVPN / OVPN2FA / NONE) по подсети CCD. Работает только с /24 |
| `_lib.ms` | **дополняет** корневую `_lib`: конвертация адресов 2FA-подсети, `getConfigUser` |
| `_lib.inv` | **общий** — живет в корне репозитория, используется обоими вариантами |
| `usr.show` / `usr.revoke` | **общие** — живут в корне репозитория; путь CRL берут из `crlfile`, историческую раскладку `certs/*.pem` ищут при заданном `legacyCertsDir` (см. `_config.sample`) |

Из базового варианта здесь **не используются**: `_reset.sh` (рабочего
reset для мультисайта нет — серверы сайтов настраиваются вручную по образцу
базового), `upd.crl`, `_renew.CA.sh`, `route-client`.

## Развертывание админ-хоста

1. Клонируем репозиторий, содержимое `multisite/` кладем в рабочую папку
   (например `/etc/openvpn`), **заменяя** одноименные файлы базового варианта
   (`_lib`, `_lib.inv`, `usr.show`, `usr.revoke`, `usr.gen.ccd`, `usr.send`
   при этом остаются из корня — они общие).
2. `cp _config.sample _config` и заполняем: список `sites`, подсети
   `<site>_openvpn_lan`/`<site>_openvpn2fa_lan` (только /24!), `sshpostfix`,
   `remoteCcdDir`, `remoteGauthDir`, доступы к Nextcloud/СМС-шлюзу/инвентори.
3. PKI: для новой инсталляции подойдет `openssl.cnf` из корня репозитория;
   если CA уже ведется отдельно (например в TinyCA) — просто указываем его
   конфиг в `sslconf`.
4. Раскладываем ssh-ключ `rsynckeyfile` на root серверов сайтов.
5. В папку `send_files/` кладем `инструкция.pdf` и `инструкция_connect.pdf`
   (в git не хранятся) — их отправляет `usr.send`.

Зависимости: `openssl`, `openvpn`, `jq`, `curl`, `ssh`,
`google-authenticator` (libpam-google-authenticator).

## Рабочий цикл

```sh
./usr.new ivanov-ii            # создать папку клиента (с оберткой на сайт: ./usr.new ivanov-ii <site>)
./usr.gen.ccd ivanov-ii chl    # выдать IP на сайте chl (создает CCD)
./usr.generate ivanov-ii       # сгенерировать ключ/серт/конфиги по всем сайтам
./usr.push ivanov-ii           # раскатать CCD и 2FA-секреты на серверы сайтов
./usr.send ivanov-ii           # отправить конфиги через Nextcloud + пароли по СМС
```

Отключение/включение: `./usr.disable ivanov-ii [site]`,
`./usr.enable ivanov-ii [site]` (без сайта — по всем).

## Известные ограничения

- `_ccd.check` (а значит и весь выбор режима 2FA) работает только для
  подсетей /24;
- reset/инициализация серверов сайтов скриптами не автоматизирована;
- 2FA-подсеть должна повторять обычную в третьем октете
  (см. `2faToNormalIp` в `_lib`).

План переноса этих наработок в базовый вариант — в [UNIFICATION.md](UNIFICATION.md).
